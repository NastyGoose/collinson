# Collinson project instructions for Claude Code

Read this file before implementing a Collinson ticket. The assessment is a single backend service that accepts a city or town and ranks seven dates for each of skiing, surfing, outdoor sightseeing and indoor sightseeing. The brief requires Node.js, GraphQL, Open-Meteo and persisted weather. It asks for a public GitHub submission with a short README and an authentic record of how decisions were made with AI assistance.

## Implementation rules

- Keep the NestJS resolver focused on orchestration and GraphQL mapping. The location module owns geocoding and stable IDs. The forecast module owns provider adapters, normalization, persistence and refresh. The activity folder computes scores from normalized weather with no I/O. Use an injectable clock for request time and freshness.
- Require exactly one city or stored location ID. Trim and validate the city, apply the optional country filter only to city searches, return ambiguity explicitly, and resolve known IDs without geocoding. Keep genuine empty searches distinct from provider failures.
- Freeze the request instant before location resolution. Derive tomorrow and the next six dates in the selected IANA timezone. Convert provider Unix timestamps by that timezone for each instant. Check actual coverage of the required local hours and preserve measurement nulls separately.
- Keep atmospheric and marine data independent. Persist normalized weather in PostgreSQL on the versioned snapshot key. Check age and coverage together. Validate every replacement before an atomic upsert. Keep provider I/O outside database transactions. After a shared refresh, check coverage for each caller's own date window.
- Preserve four groups of seven dates for a resolved location through partial or total weather-source failure. Return typed source status and day-level availability. An unavailable day has null score and rank. A valid, up-to-date marine snapshot can have no usable wave data.
- Keep scoring deterministic, versioned and explainable. Use the scoring v1 rules and precedence in [ADR 0005](docs/adr/0005-deterministic-activity-scoring.md). Apply the marine limit only after source and measurement checks. Keep zero measurements intact. Use the score explanations to describe weather suitability for a generic visitor.
- Follow the target code structure in [ADR 0006](docs/adr/0006-module-layout-and-naming.md). Its working form is [`.claude/rules/code-structure.md`](.claude/rules/code-structure.md): singular domain folders, `<domain>.<role>.ts` files, types and constants apart from logic, unit specs in `test/unit/`, the injected logger and the module boundaries. `npm run lint:structure` enforces the boundaries. Ask the read-only [`architect`](.claude/agents/architect.md) agent where new code belongs, or have it review a change or audit the codebase.

## Verification and handoff

- Use checked-in Prisma migrations for development and isolated PostgreSQL tests. Keep local setup reproducible with Compose and document the commands once the scripts exist. Use a fixed clock and controlled provider fixtures in automated tests. Keep live-provider smoke checks optional and separate from CI.
- Match verification to the ticket. Cover scoring and calendar edges with unit tests, migrations and durable snapshot behavior with integration tests, and the typed GraphQL contract with E2E tests. Report the actual commands, outcomes and any verification gaps.
- Keep one implementation ticket per PR and link the ticket. Keep dated notes on material assumptions, alternatives, AI contributions and changes of mind as they occur, in [`docs/engineering-notes.md`](docs/engineering-notes.md). When a decision changes, update the affected spec or design and document the change in an ADR. Keep scratch notes, secrets and personal material out of the submission.
- For the final submission, verify the README from a clean checkout, including setup, migrations, run and test commands, GraphQL examples, assumptions and Open-Meteo attribution. Review content before publication. Assessor notification is a separate submission action that requires explicit authorization.
- End any spec-finalization handoff with a copy-ready developer prompt covering the workspace, first ready ticket and acceptance criteria, source links, scope and verification.

Forecast persistence ([ARC-46](https://linear.app/archiview/issue/ARC-46/dev-persist-and-refresh-open-meteo-snapshots)) adds `src/forecast`: the local date window and coverage check (now in `src/calendar`), the Open-Meteo atmospheric and marine adapters, the `forecast_snapshots` table and `ForecastService.getWeather`, which returns a FRESH, STALE or UNAVAILABLE result per source. Activity scoring ([ARC-47](https://linear.app/archiview/issue/ARC-47/dev-implement-deterministic-activity-scoring-v1)) adds `src/activity`: `scoreActivities`, a pure function from the window and each source's normalized forecast (null when unavailable) to four ranked groups shaped like the GraphQL `RankedDay`, and `test/fixtures/scoring-weather.ts`, which builds weather per local date and hour. The GraphQL contract ([ARC-48](https://linear.app/archiview/issue/ARC-48/dev-wire-the-graphql-activity-forecast-contract)) adds `src/activity-forecast`: the Technical Design SDL, a resolver that freezes the request instant, resolves the location, derives the window once and scores both sources, `DomainErrorFilter` for the documented error codes and a `formatError` hook that masks every error outside the documented and Apollo request codes as INTERNAL_SERVER_ERROR. `test/support/fake-open-meteo.ts` is the fake Open-Meteo for all three APIs that the integration and E2E tiers share; `test/support/forecast-app.ts` holds the forecast queries and an app start against the per-run database. The scenario matrix ([ARC-49](https://linear.app/archiview/issue/ARC-49/e2e-verify-location-date-and-forecast-failure-scenarios)) lives in `test/e2e/forecast-scenarios.e2e-spec.ts`: stored-ID lookup during a geocoding outage, local midnight and DST, cold, warm and restart reuse, bounded stale fallback, invalid replacements, all-null, partial and distant marine data and partial or complete source failure; `activity-forecast.e2e-spec.ts` keeps the contract cases. Submission readiness ([ARC-50](https://linear.app/archiview/issue/ARC-50/dev-make-the-submission-reproducible-from-a-clean-checkout)) adds `.github/workflows/ci.yml` (format, lint, typecheck, all three test tiers, then migrate, boot and `health` against a PostgreSQL service), the runnable request bodies in `examples/`, the optional `npm run smoke:live` check and its manual `live-smoke.yml` workflow, and [`docs/engineering-notes.md`](docs/engineering-notes.md), where dated decisions, AI involvement and scope cuts go from now on. What remains is the submission itself: making the repository public and notifying the assessor, each of which needs explicit authorization. PR documentation skills ([ARC-53](https://linear.app/archiview/issue/ARC-53/dev-add-changes-notes-and-testing-notes-skills-for-every-pr)) add `changes-notes` and `testing-notes`, which publish a private "what changed" page and a criteria-and-evidence page for each PR; `changes-notes` replaces `pr-walkthrough`. The ADR 0006 refactor ([ARC-54](https://linear.app/archiview/issue/ARC-54/dev-refactor-the-codebase-to-match-adr-0006)) ran in two parts: the layout ([ARC-56](https://linear.app/archiview/issue/ARC-56/dev-apply-the-adr-0006-module-layout-and-remove-the-structure-baseline)) and the shared `nestjs-pino` logger ([ARC-57](https://linear.app/archiview/issue/ARC-57/dev-use-the-shared-nestjs-pino-logger-by-injection)), which every class that logs takes by injection, with `LOG_LEVEL` and silent test runs. The GraphQL Tools patch ([ARC-58](https://linear.app/archiview/issue/ARC-58/dev-patch-the-affected-graphql-tools-runtime-dependency)) adds a scoped `overrides` entry under `@apollo/server` in `package.json`. It aligns `@graphql-tools/merge`, `schema` and `utils` with the versions `@nestjs/graphql` pins, which removes GHSA-c4qx-w738-7hr3. Apollo Server 5.5.2 caps these packages to keep Node 20 installs working, and this project runs on Node 24. Remove the override when Apollo lifts the cap (see the engineering notes). Request-error normalization ([ARC-59](https://linear.app/archiview/issue/ARC-59/dev-normalize-graphql-request-errors-and-location-not-found-responses)) adds the global `RequestErrorFilter` (`src/activity-forecast/activity-forecast-request.filter.ts`), which answers a body that does not parse with a fixed GraphQL-shaped `BAD_REQUEST` and Nest's route-not-found 404 without the path. `formatGraphQLError` gives fixed messages to variable coercion errors (without `field`), parse errors, validation errors on input literals and operation resolution errors, and reports graphql-js's extra error after 50 variable errors as `BAD_USER_INPUT`. `LocationNotFound` messages are fixed too. `GRAPHQL_INTROSPECTION` sets introspection explicitly (off by default under `NODE_ENV=production`), `test/support/introspection-env.ts` pins it on for the database tiers, and `test/e2e/request-errors.e2e-spec.ts` holds the sentinel regressions.

Project layout ([ADR 0006](docs/adr/0006-module-layout-and-naming.md)): one singular folder per domain under `src/` (`location`, `forecast`, `activity`, `activity-forecast`), the pure `src/calendar/`, and infrastructure folders (`clock`, `config`, `http`, `prisma`, `health`, `logger`). Files are named `<domain>[-<subject>].<role>.ts`, with types and constants in `.types` and `.constants` files. GraphQL SDL lives beside each module as `*.graphql`; Prisma schema and migrations in `prisma/`; the generated client in `src/generated/` (git-ignored, rebuilt on `npm install`). Unit specs live in `test/unit/`, mirroring `src/`. Database-backed tiers live in `test/integration` and `test/e2e`, and each run uses its own throwaway database. Structure rules and the architect agent ([ARC-52](https://linear.app/archiview/issue/ARC-52/dev-record-structure-rules-and-add-an-architect-agent-with-a-ci)) add ADR 0006, `.claude/rules/code-structure.md`, `.claude/agents/architect.md` and the `lint:structure` CI step, which has run without a known-violations baseline since ARC-56.
